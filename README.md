# channel-integration

여러 외부 숙박 공급사의 상품을 하나의 숙박 상품 모델로 모아 검색하는 연동 백엔드입니다.

## 실행

```bash
./gradlew :mock-supplier:bootRun   # Mock 공급사 (9090)
./gradlew :app:bootRun             # 애플리케이션 (8080), 기동 시 숙소 목록 동기화
./gradlew test
```

```bash
curl "localhost:8080/api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0"
curl -X POST "localhost:9090/control/a/mode?value=error"   # normal | error | no-response | slow
curl -X POST "localhost:8080/internal/suppliers/a/sync"    # 숙소 목록 재동기화
```

- API 문서: http://localhost:8080/swagger-ui.html

## 흐름

```
[기동] 공급사 숙소 목록 → 내부 숙소·객실 타입 식별자로 매핑 저장
[검색] 매핑에서 코드를 50개씩 묶음 → A, B 병렬 조회 → 표준 모델로 정규화 → 병합
```

## 설계 결정

- 요금: 요청 기간 전체의 세금 포함 총액 + 통화 + 조식 포함 여부
  - B 가 기간 총액만 주므로 공통분모는 이것뿐이다.
  - A 의 날짜별 내역은 `daily` 로 남기고 B 는 `null`. B 는 날짜별 요금과 세액을 잃는다.
  - 같은 객실도 공급사마다 조식 조건이 달라 조식 여부를 요금 옆에 둔다.
- 연박 예약 가능 객실 수: 숙박일별 잔여 수의 최솟값. 하루라도 없으면 0.
- 예약 불가(0) 상품은 응답에서 뺀다. 날짜·인원 검색에서 고객이 할 수 있는 일이 없다.
- 매핑: (공급사, 숙소 코드), (숙소, 객실 타입 코드) 로 유일. upsert 로 같은 상품은 같은 식별자, 사라지면 비활성화.
- 숙소 목록은 기동 시와 수동 API 로만 받는다. 거의 바뀌지 않으므로 검색마다 부르지 않는다. 실패하면 기존 매핑 유지.
- 숙소가 수천 개면: 공급사 API 가 50개까지 받으므로 50개씩 나눠 병렬 호출. 공급사당 동시 4개로 제한.
- MVC + WebClient: JPA 라 어차피 블로킹이고, 병렬·타임아웃·재시도는 WebClient 와 Resilience4j 로 충분하다. 블로킹은 검색 서비스 한 곳.

## 연동 견고성

- 타임아웃
  - 연결 1초: 넘으면 장애다.
  - 재고 응답 3초: 50개 조회 정상 응답은 1초 안이다.
  - 목록 응답 10초: 응답이 크고 사용자가 기다리지 않는다.
  - 검색 전체 5초: 사용자 대기 상한. 개별 타임아웃보다 우선한다.
- 부분 실패: 한 공급사가 실패해도 200 으로 나머지를 반환하고 `failures` 에 실패 공급사와 사유를 담는다.
- 실패 판정 통일: A 는 HTTP 상태, B 는 HTTP 200 + `resultCode`. 둘 다 같은 사유로 바꾼다.

| 사유 | A | B | 재시도 |
|---|---|---|---|
| UNAVAILABLE | 503 | E503 | O |
| RATE_LIMITED | 429 | E429 | O |
| SUPPLIER_ERROR | 500, 5xx | E500 | O |
| TIMEOUT | 타임아웃 | 타임아웃 | O |
| BAD_REQUEST | 400 | E400 | X |
| UNAUTHORIZED | 401 | E401 | X |
| MALFORMED | 파싱 실패 | 파싱 실패, resultCode 없음 | X |

- 재시도는 1회, 300ms 후. 응답 안의 항목 하나가 깨지면 그 항목만 버린다.

## 스펙과 달라진 점

- 응답 버퍼 한도를 256KB 에서 16MB 로 올렸다. 30박 응답이 실패했다.
- 숙소 코드를 URI 변수로 인코딩한다. `{`, `+` 가 요청을 깨뜨렸다.
- 같은 공급사 동기화는 잠금으로 겹치지 않게 했다. 기동·수동 동기화가 겹쳐 유일 제약 위반이 났다.
- 동기화 대기를 11초에서 21.3초로 늘렸다. 목록 호출 재시도가 끝날 수 없었다.
- 인원은 성인·아동 각 20명 이하. 합계가 넘쳐 인원 필터를 통과했다.
- 공급사 호출은 트랜잭션 밖에서 기다리고 반영만 트랜잭션으로 묶는다.
- 지표·로그 코드, 아키텍처 테스트, 일부 종단 테스트는 구현하지 않았다.

## AI 활용

Claude 를 설계 피드백, 스펙 작성, 구현, 점검에 사용했습니다.

- 수용: 수천 개 숙소를 페이징으로 풀려던 생각을, 50개는 공급사 API 제한이라는 지적을 받고 청크 병렬 호출로 바꿨다.
- 수정: AI 설계 초안을 직접 줄이고 고쳤다. 받을 수 있는 데이터를 모두 받는 모델은 null 이 가득 찬다고 보고 공통분모 모델로 바꿨다.
- 구현: 스펙 단계마다 AI 가 테스트를 먼저 쓰고 구현했고, 결과를 확인한 뒤 직접 커밋했다.
- 거부: AI 가 직접 커밋한 것은 취소하고 커밋은 모두 직접 했다.
- 점검: 구현 후 스펙 대조와 정확성 리뷰를 맡겨 나온 버그 5개를 스펙에 추가해 고쳤다.
