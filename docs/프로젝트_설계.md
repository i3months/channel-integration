# 2. 프로젝트 설계

## 2.1 기술 스택

- 언어: Java 21
- 프레임워크: Spring Boot 3.4, Spring MVC
- 빌드: Gradle, Kotlin DSL
- DB: H2, Spring Data JPA
  - 인메모리 디비를 써야 실행하기 쉽다. 외부 의존성 도커로 묶으면 괜히 귀찮아진다. 나중에 mysql postgresql로 이동하는것도 간단하다.
- HTTP 클라이언트: Spring WebClient (spring-boot-starter-webflux 의존성만 추가하고 서버는 MVC 사용)
- 회복탄력성: Resilience4j (시간제한 관련해서는 WebClient 자체 타임아웃을 사용함.)
- 지표: Micrometer + Spring Boot Actuator
- API 문서: SpringDoc OpenAPI
- 테스트: JUnit 5, AssertJ, MockWebServer (공급사 응답 재현용)
- Mock 공급사: 같은 저장소 안의 별도 Gradle 서브모듈, 포트 9090로 애플리케이션과 다른 포트로 지정함.

## 2.2 MVC + WebClient 근거

- 근거
  - JPA를 쓰면 어차피 블로킹이다.
  - 병렬 호출, 타임아웃, 재시도는 WebClient로 충분함.
- 버린것
  - 전면 WebFlux.
  - 컨트롤러까지 Mono 를 반환하는 구조

## 2.3 숙박 상품 모델 통합

- 원칙
  - 서플라이어 A와 B를 살펴보고 결정함.
  - 표준 필드는 두 공급사가 모두 줄 수 있는 것만 둔다. (여기서 서플라이어는 A와 B로 한정함)
  - 한쪽만 주는 정보는 선택 필드로 두고 nullable. 도메인 Price 안에 nullable 로 두고 어댑터가 채운다. 어댑터는 표준 Offer 만 반환하므로 도메인을 거치지 않으면 응답까지 갈 길이 없다.
- 단위
  - 숙소(Stay): 내부 숙소 식별자, 숙소명, 출처 공급사
  - 객실 타입(RoomType): 내부 객실 타입 식별자, 객실 타입명, 최대 수용 인원
  - 판매 조건(Offer): 검색 1건에 대한 객실 타입 하나의 재고와 요금. (DB저장안함)
- 요금 표준
  - 선택: 요청 기간 전체 총액, 세금 포함, 통화 코드, 조식 포함 여부, 박수
  - 근거: 고객이 결제하는 금액은 세금 포함 총액이다. B 는 총액만 준다. 조식 포함 여부는 같은 객실이라도 다르므로 요금과 함께 보여야 비교가능함.
  - 선택 필드: 일별 내역(날짜, 세전 단가, 세액). A 만 채우고 B는 null
  - 잃는 것: B 상품은 일별 요금과 세액을 보여줄 수 없다. 알고 선택함.
  - 버린 것: B 의 taxIncluded. 항상 true 라 정보가 없다.
- 재고 표준
  - 선택: 예약 가능 객실 수 하나. 요청 기간 전체를 예약할 수 있는 객실 수.
  - 판정: 숙박일마다 잔여 객실 수를 받아 그 최솟값을 쓴다. 숙박일 중 하루라도 데이터가 없으면 0 으로 처리함. 0이면 예약 불가라고 보면 된다.
  - 근거: N 박을 한 객실로 이어서 묵으려면 매일 그 객실이 남아 있어야 한다. 그 최솟값을 가져다 쓰면 됨.
- 예약 불가 상품
  - 선택: 응답에서 제외한다.
  - 근거: 검색 조건이 날짜와 인원뿐이라, 예약 불가 상품은 고객이 할 수 있는 행동이 없다.
- 통화
  - 선택: 통화 코드를 그대로 노출하고 환산하지 않는다. 예시 데이터는 모두 KRW 다.
- 중복 상품
  - 선택: 공급사가 다르면 별개 상품으로 노출한다. 하나로 병합하지 않음.
  - 근거: 공급사 간 공통 키가 없다. 이름으로 추정 매칭하면 오매칭 위험이 있고, 같은 객실이라도 조식 등 조건이 달라 하나로 합치면 비교가 왜곡된다.

## 2.4 공급사 코드와 내부 식별자 매핑

- 매핑만 저장하고 요금 및 재고 데이터는 저장하지 않음.
- 유일 제약은 반드시 둔다. upsert 가 이 제약을 기준으로 동작하기 때문임.
- 테이블
  - supplier_stay
    - 컬럼: id, supplier_code, supplier_hotel_code, name, active, created_at, updated_at
    - 유일 제약: (supplier_code, supplier_hotel_code)
  - supplier_room_type
    - 컬럼: id, stay_id(supplier_stay.id 참조), supplier_room_type_code, name, max_occupancy, active, created_at, updated_at
    - 유일 제약: (stay_id, supplier_room_type_code)
- 식별자 안정성
  - 같은 (공급사, 숙소 코드) 가 다시 오면 기존 id 를 반환한다. upsert 처리함.
  - 목록에서 사라진 숙소나 객실 타입은 active 값을 false 로 바꾼다. 식별자가 재사용되면 안됨.
  - 이름이나 최대 인원이 바뀌면 갱신한다. 식별자는 그대로다.
- 숙소 목록 API 호출 시점
  - 선택: 앱 기동 시 공급사별로 한 번 동기화한다. 그리고 수동 재동기화 엔드포인트를 둔다.
    - POST /internal/suppliers/{supplierCode}/sync
  - 근거: 숙소 목록은 자주 바뀌지 않는다. 검색마다 부르면 낭비가 심함. 외부 호출은 최소화해야함. 그리고 검색 지연이 목록 API 에 묶인다. 앱 메인에서 보여줘야 되기도 하니까.
  - 기타: 스케쥴러로 api호출하는건 구현하지 않음.
- 동기화 실패 처리
  - 목록 API 가 실패하면 기존 매핑을 유지한다. 앱은 그대로 켜져야 한다.
  - 실패는 로그와 지표로 남긴다 꼭!!!.
  - 매핑이 하나도 없는 공급사는 호출하지 않는다. 대신 failures 에 NO_MAPPING 으로 드러낸다. 조용히 빠지면 장애인지 원래 없는지 구분이 안됨.
- 동기화 트랜잭션 묶음
  - 공급사 하나의 동기화는 하나로 묶는다.

## 2.5 공급사 연동 어댑터 설계

- Port and Adapter 아키텍처를 사용함. 도메인을 격리시키기 좋다.
- 포트는 도메인 쪽에 둔다
  - SupplierCatalogPort
    - fetchCatalog(): 공급사의 전체 숙소와 객실 타입 목록을 표준 형태로 반환
  - SupplierAvailabilityPort
    - fetchAvailability(hotelCodes, checkIn, checkOut, adults, children): 최대 50개 코드에 대한 재고와 요금을 표준 Offer 목록으로 반환
  - 두 포트를 나눈 근거: 목록은 기동 시, 재고는 검색마다 갱신됨. 목록 실패는 매핑 유지하고 재고 실패는 부분 실패라서 분리함.
- 어댑터는 공급사별 패키지에 둔다
  - supplier-a 패키지: A 전용 요청·응답 DTO, WebClient 호출, A 응답을 표준으로 바꾸는 변환기. A 실패 판정
  - supplier-b 패키지: 마찬가지임 B 전용
  - 어댑터 하나가 두 포트를 모두 구현한다. 공급사 코드(A, B) 를 반환하는 메서드를 갖는다.
- 등록
  - 스프링이 모든 어댑터를 List 로 주입한다. 레지스트리가 공급사 코드로 찾는다.
  - 공급사별 base URL, API 키, 타임아웃은 설정파일 suppliers.{code} 아래에 둔다.
  - 어댑터는 모든 공급사 요청에 X-Api-Key 헤더를 붙인다. 두 공급사 공통 규약임.
- 서플라이어 추가 시 수정해야 할 부분
  - 새 패키지: DTO, 어댑터, 변환기, 실패 판정
  - 설정파일에 suppliers.{code} 블록 하나 (base URL, API 키, 타임아웃)
  - 고치지 않는 것: 도메인, 검색 서비스, 매핑 저장, 컨트롤러, 응답 DTO
- 경계 규칙
  - 공급사 DTO 는 어댑터 패키지 밖으로 나가지 않는다. 아키텍처 테스트 로 강제한다.
  - 어댑터는 예외를 던지지 않는다. 성공 또는 실패 사유를 담은 결과 객체를 반환한다.

## 2.6 통합 검색 API

- 계약
  - GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
  - 요구사항이 고정한 최소 계약. 파라미터 이름은 바꾸지 않는다.
  - 검증: checkOut 은 checkIn 보다 나중에 함. adults 는 1 이상. children 은 0 이상. 위반 시 400 뱉기.
  - 검색 대상은 active 인 모든 매핑이다. 지역 필터, 정렬, 페이징은 고려하지 않음.
- 응답 구조
  - checkIn, checkOut, nights, adults, children
  - items[]
    - stayId, stayName
    - roomTypeId, roomTypeName
    - maxOccupancy
    - availableRooms
    - supplier
    - price
      - totalAmount, currency, breakfastIncluded, nights
      - daily[] (선택, A 만): date, nightlyRate, taxAmount
  - failures[]
    - supplier, reason, message
    - 비어 있으면 문제없는것
- 처리 흐름
  - 요청 검증
  - 매핑 DB 에서 active 숙소를 공급사별로 묶는다
  - 공급사별로 숙소 코드를 50개씩 청크로 나눈다
  - WebClient를 사용하니 청크마다 fetchAvailability 를 Mono 로 만든다
  - 공급사 안에서 동시 청크 수는 4개로 제한한다. Too Many Request를 피해야함. 다만 이 값은 설정파일에서 넣어주도록 해야함.
  - 모든 Mono 를 합치고 전체 시간 예산 안에서 block 한다
  - 어댑터가 준 Offer 의 공급사 코드를 매핑 DB 로 바꿔 내부 식별자를 붙인다. 매핑에 없는 코드는 버리고 로그를 남긴다
  - availableRooms 가 0 인 항목을 제외한다
  - 청크 실패는 failures 에 모은다. 같은 공급사의 실패는 하나로 합치고 실패 청크 수를 message 에 적는다
  - 청크 안에서 항목 하나만 깨지면 그 항목만 버리고 원본 조각과 사유를 로그에 남긴다. 나머지 항목은 정상 처리. 청크 전체가 파싱이 안 되면 청크 실패 MALFORMED
- 숙소가 수천 개일 때
  - 우선은 50개 청크 병렬 호출로 처리한다. 3천 개면 공급사당 60번 호출이고 동시 4개면 15 라운드.
  - 응답 시간이 시간 예산을 넘으면 끝난 청크까지만 응답하고 나머지는 failures 에 타임아웃 처리함.
  - 근본 대책은 요금·재고 캐시다. 설계만 함. 키는 (공급사, 숙소 코드, checkIn, checkOut, adults, children), TTL 60초. 같은 키 동시 요청은 하나만 공급사로 보낸다. 예약 직전에는 캐시를 우회해 다시 조회한다.

## 2.7 연동 견고성

- 타임아웃
  - 연결 타임아웃 1초. 근거: 연결 자체가 1초를 넘으면 네트워크나 공급사 장애임. 기다려도 뭐 없음.
  - 응답 타임아웃 3초. 근거: 50개 숙소 벌크 조회 한 번의 정상 응답은 1초 안이어야 한다. 3초 넘어가면 고장난거로 인식함.
  - 검색 전체 시간 예산 5초. 근거: 이거 지나고도 안되면 유저가 앱 끈다.
  - 전체 예산이 우선이다. 응답 타임아웃 3초에 재시도까지 더하면 6초를 넘길 수 있으므로, 재시도 중이라도 예산을 넘기면 TIMEOUT 으로 끊고 끝난 청크까지만 응답한다.
  - 모두 설정파일로 분리함.
- 부분 실패 허용
  - 공급사 하나가 전부 실패해도 나머지 공급사 결과로 200 을 반환한다.
  - 모든 공급사가 실패하면 items 는 비고 failures 만 있다. 그래도 200 이다. 검색 요청은 제대로 들어갔으니까..
- 실패 판정 통일
  - 어댑터는 모든 실패를 enum 으로 다룬다.
    - TIMEOUT: 연결 또는 응답 타임아웃
    - UNAVAILABLE: A 503, B E503
    - RATE_LIMITED: A 429, B E429
    - BAD_REQUEST: A 400, B E400
    - UNAUTHORIZED: A 401, B E401
    - SUPPLIER_ERROR: A 500, B E500, 그 외 5xx
    - MALFORMED: JSON 파싱 실패, 필수 필드 누락, B 의 200 인데 resultCode 없음
    - NO_MAPPING: 매핑이 없는 공급사
  - A 는 HTTP 상태 코드로, B 는 HTTP 200 본문의 resultCode 로 판정한다. B 의 resultCode 가 0000 이 아니면 HTTP 200 이어도 실패다.
  - 재시도 가능: TIMEOUT, UNAVAILABLE, RATE_LIMITED, SUPPLIER_ERROR
  - 재시도 불가: BAD_REQUEST, UNAUTHORIZED, MALFORMED, NO_MAPPING
- 재시도
  - 재시도 가능 사유에 한해 1회. 대기 300ms 고정. 한 번 까지는 재시도 하지만 넘어가면 끝
  - 재시도 후에도 실패면 원래 사유로 failures 에 넣는다.
- 서킷 브레이커 (설계만, 구현하지 않음)
  - 공급사 단위로 둔다. 최근 20회 중 실패율이 절반 이상이면 30초간 열어둔다. 이 때는 외부 api 호출 안하고 UNAVAILABLE 처리.

## 2.9 Mock 공급사

- 서브모듈 mock-supplier로 사용함. 포트는 9090
- 엔드포인트
  - GET /a/v1/hotels, GET /a/v1/availability
  - GET /b/api/properties, GET /b/api/search
  - POST /control/{supplier}/mode?value=normal|error|no-response|slow
- 모드
  - normal: 부록 예시 구조의 정상 응답
  - error: A 는 HTTP 503, B 는 HTTP 200 + resultCode E503
  - no-response: 연결 후 응답 없음 (긴 sleep)
  - slow: 2초 뒤 정상 응답. 응답 타임아웃 3초 안이라 성공해야 한다. 타임아웃 경계 확인용.
- 목록 API 에도 error 모드를 건다. 기동 시 동기화 실패를 종단 테스트에서 재현하기 위함.

## 2.10 연동 지표

- Micrometer 로 아래를 남기고 Actuator /actuator/metrics 로 노출한다
  - supplier.call.count, 태그: supplier, api(catalog|availability), outcome(success|실패 사유)
  - supplier.call.duration, 태그: supplier, api. 히스토그램 켜서 p50, p95, p99
  - search.duration, 태그: partial(true|false)
  - search.count, 태그: partial
- 파생 지표
  - 공급사별 성공률 = success / 전체

## 2.12 테스트 전략

- 단위 테스트
  - A 변환기: 일별 단가와 세액을 합산해 총액이 나오는지. 예시 데이터로 429,000 확인
  - B 변환기: 총액을 그대로 쓰는지. 예시 데이터로 452,000 확인
  - 연박 판정: 잔여 3, 1, 5 면 1. 잔여 2, 0, 4 면 0. 날짜 누락이면 0
  - 실패 판정: A 상태 코드별, B resultCode 별로 FailureReason 이 맞게 나오는지
  - 청크 분할: 120개 코드가 50, 50, 20 으로 나뉘는지
- 어댑터 통합 테스트 (MockWebServer)
  - 정상 응답 변환
  - A 503, B 200+E503 이 같은 UNAVAILABLE 인지
  - 응답 없음이 응답 타임아웃 안에 TIMEOUT 으로 끝나는지
  - 재시도 가능 사유에서 정확히 한 번 더 부르는지
- 서비스 통합 테스트
  - A 실패, B 성공이면 B 결과와 failures 에 A 가 있는지
  - 둘 다 실패면 items 비고 200 인지
  - 예약 불가 항목이 빠지는지
  - 매핑 없는 코드가 버려지는지
- 동기화 테스트
  - 두 번 동기화해도 id 가 같은지
  - 목록에서 사라진 숙소가 active false 가 되는지
  - 목록 API 실패 시 기존 매핑이 남는지
- 종단 테스트
  - Mock 서브모듈을 띄우고 실제 HTTP 로 검색. 네 모드 각각 한 번씩
- 아키텍처 테스트
  - 공급사 DTO 가 어댑터 패키지 밖에서 참조되지 않는지
