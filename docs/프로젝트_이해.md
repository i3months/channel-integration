# 1. 프로젝트 이해

- 외부 숙박 상품 공급사의 상품을 하나의 플랫폼으로 통합하는 연동 백엔드 시스템
  - 서비스에서 보여지는 데이터를 모으는 프로젝트라고 이해됨.
  - 여러 공급사의 데이터를 하나의 형식으로 통합하는게 중요해보인다.
  - 크롤링? 아니면 공급사에서 제공하는 api? 아마 api를 사용하는 것으로 보임.

- 공급사마다 API 스펙이 다르다. 같은 숙박 상품을 다른 방식으로 표현한다. 일관된 숙박 모델로 통합해야 함.
  - 공통 데이터 모델이 있어야 할 듯.
  - 테스트를 하나씩 작성해보는게 좋겠다. 여러 벤더사에서 가져오는 데이터를, 내가 정한 데이터 모델로 바꾸는 방식.
  - 개발 방식은 TDD와 SDD를 섞어서 진행하는게 좋아보인다.
  - 각 작업을 구현할 때는 TDD로, 방향과 요구사항은 SDD 로 진행하자.

- Spring WebClient를 사용하지만 WebFlux 전면 도입은 요구하지 않음
  - 기본적으로 리액티브 프로그래밍으로 알고 있음.
  - 외부 api를 다룰 때 타임아수, 재시도 같은거를 선언적으로 다룰 때 사용하면 될듯.

- 연동 지표 및 모니터링 설계
  - 당장 생각나는 것 정리해보기
  - 응답 시간 / 호출 수 / 타임아웃 비율
  - 이건 ai 리서치 돌리고 결정하는게 좋겠다.

- 회복탄력성 라이브러리
  - 외부 호출이 실패하거나 성능이 느려질 때 사용하자.
  - WebClient에 resilience4j 를 끼워서 사용하는게 될텐데. 검토해보고 사용하자.

- 실제 외부 서비스는 호출하지 않는다. Mock Supplier를 직접 구성함
  - 호출하지 않더라도 여러 벤더사의 서플라이어가 어떻게 구성되어있는지 알면 구현에 도움이 될 듯.
  - ai 한테 리서치 시키고 결과 받아와서 구현에 참고하자.

- 공급사마다 API가 다르다. 날짜별 1박 단가를 주는 경우도 있고 숙박 전체 총액을 주는 경우도 있고..
  - 내가 정해야 할 건, 내 서비스에 어떤 식으로 보여줄지를 정하는 것과 데이터를 어떻게 받아올지를 정하는 것.
  - 즉, 받아올 수 있는 모든 데이터를 정의한 후, 벤더사의 api 스펙에 맞춰서 최대한 받아온다.
  - 그리고 나서 내 서비스에 보여줘야 하는 형태로 데이터를 가공하는 식으로 작업하면 되겠다.

- 상태 코드 관련 처리
  - 실패를 알리는 방식이 다양하니, 모든 경우를 커버할 수 있어야 한다.
  - 서플라이어 A B 스펙이 있으니 참고하자. 굳이 내가 예외케이스를 생각하지 않고 A와 B만 커버하면 될듯.

- 숙소 객실 요금 재고를 어떤 단위로 잡을지는 직접 정의
  - 내 서비스에서 어떤 형태로 데이터를 보여줄지는 내가 직접 정의
  - 이거는 ai에게 리서치 시키고 받아온 결과를 바탕으로 결정해보자.

- 공급사 코드와 내부 식별자 매핑을 데이터베이스에 저장
  - 외부 서플라이어에서 받은 데이터를 모두 저장할 필요는 없다.
  - 코드와 식별자 매핑은 저장해야 함. 이래야 같은 식으로 서플라이어에 다시 조회 할 수 있으니까

- 언제 호출할지
  - 서플라이어에서 가격이 바뀌는 경우도 있을건데
  - 외부 api 를 너무 많이 호출하면 타임아웃이 걸리거나 제한 먹을 수 있음.
  - 메인 페이지에서 숙소 추천이 필요한 경우도 있을거고..
  - 숙소는 바뀌지 않지만 숙소의 상태는 바뀐다.
  - 예약보다 검색이 훨씬 많을건데 예약 직전에는 다시 조회하고 검색은 TTL 오래 잡는것도 좋아보인다.
  - 캐시 설계도 필요할텐데.. 이건 나중에 구체화..

- 중복 상품 병합
  - 두 가지 벤더사에서 같은 숙소를 가져올 수 있지만, 서로 다른 숙소로 취급하자.

- 연동 어댑터
  - 앞서 설계한대로 어댑터를 구현하면 됨.
  - 새로운 서플라이어를 추가하더라도 수정하지 않도록 잘 추상화하는게 중요할듯.

- 통합 검색
  - 여러 서플라이어를 병렬 조회 여기서 webclient 사용
  - 어댑터를 통해서 조회한 결과를 받는거니까. 여기서는 그냥 잘 받아서 보여주기만 하면 된다.
  - 숙소가 수천 개일 때는? 당연히 페이징 처리 해야 하는거 아닌가
  - 연박 검색에도 대응할 수 있도록 데이터 모델을 구축해 두는게 좋아보임
  - 예약 불가 상품은 응답에서 뺴는게 낫지 않나? 내가 사용자라면 예약 가능한 것만 보고 싶을텐데.. 앱 사용할때도 이렇게 생각했었고..

- 연동 견고성
  - 이건 앞에서 설계를 제대로 했다면 그대로 가면 된다.
