# 3. 구현 스펙

## 3.0 이 문서의 사용법

- 이 문서는 구현의 유일한 기준이다. 구현자는 이 문서만 보고 코드를 쓴다. 설계 문서(프로젝트_설계.md)는 근거를 보러 갈 때만 참고한다.
- 문서 간 충돌이 있으면 스펙 > 설계 > 이해 순으로 우선한다. 충돌을 발견하면 코드를 스펙에 맞추고, 충돌 사실을 JOURNAL.md 에 적는다.
- 요구 항목에는 ID 를 붙였다. 테스트 이름과 커밋 메시지에 이 ID 를 넣어 추적 가능하게 한다.
  - SK: 골격, DM: 도메인, MP: 매핑 저장, AD: 어댑터 공통, SA: Supplier A, SB: Supplier B, SY: 동기화, SR: 검색, API: 검색 API, MK: Mock, OB: 지표와 로그, T: 테스트
- 표기 규칙
  - "해야 한다": 필수. 어기면 스펙 위반.
  - "한다": 필수. 위와 같다. 문장 흐름상 쓴 것.
  - "해도 된다": 선택.
- 구현 순서는 3.13 을 따른다. TDD 로 진행한다. 테스트 명세는 3.12 에 있다.

## 3.1 프로젝트 골격 (SK)

- SK-01 저장소 루트에 Gradle 멀티 모듈 프로젝트를 만든다. Kotlin DSL 을 쓴다.
  - 루트 프로젝트 이름: channel-integration
  - 모듈: app (본 애플리케이션), mock-supplier (Mock 공급사)
- SK-02 언어와 프레임워크
  - Java 21. 도메인 타입은 record 를 우선 사용한다. Lombok 은 쓰지 않는다.
  - Spring Boot 3.4 최신 패치 버전.
  - app 의존성: spring-boot-starter-web, spring-boot-starter-webflux (WebClient 용, 서버는 MVC), spring-boot-starter-data-jpa, spring-boot-starter-validation, spring-boot-starter-actuator, h2, resilience4j-spring-boot3, resilience4j-reactor, springdoc-openapi-starter-webmvc-ui, micrometer-core
  - app 테스트 의존성: spring-boot-starter-test, okhttp mockwebserver, archunit-junit5, reactor-test, 그리고 project(":mock-supplier") (종단 테스트용)
  - mock-supplier 의존성: spring-boot-starter-web 만.
- SK-03 app 의 루트 패키지는 com.stayhub 다. 메인 클래스는 com.stayhub.StayHubApplication.
  - mock-supplier 의 루트 패키지는 com.mocksupplier 다. 메인 클래스는 com.mocksupplier.MockSupplierApplication.
  - 두 루트를 분리하는 이유: 종단 테스트에서 mock-supplier 가 app 의 테스트 클래스패스에 올라간다. 같은 루트면 app 의 컴포넌트 스캔이 Mock 컨트롤러까지 집어 올린다.
- SK-04 app 의 패키지 구조. 이 구조를 그대로 만든다.
  - com.stayhub.domain: Stay, RoomType, Offer, Price, DailyRate, SupplierCode, FailureReason, SupplierResult, StaySearchCriteria, CatalogEntry, CatalogRoomType
  - com.stayhub.domain.port: SupplierCatalogPort, SupplierAvailabilityPort, SupplierAdapter, StayMappingRepository
  - com.stayhub.application: SearchStaysService, SyncSupplierCatalogService, SupplierRegistry, SearchResult, SearchFailure, SyncResult, StartupCatalogSync
  - com.stayhub.adapter.in.web: SearchController, SupplierSyncController, 응답 DTO 들, ApiExceptionHandler
  - com.stayhub.adapter.out.supplier.common: SupplierCallExecutor, SupplierProperties, IntegrationProperties, WebClientFactory
  - com.stayhub.adapter.out.supplier.a: SupplierAAdapter, SupplierADtos, SupplierAMapper, SupplierAFailureMapper
  - com.stayhub.adapter.out.supplier.b: SupplierBAdapter, SupplierBDtos, SupplierBMapper, SupplierBFailureMapper
  - com.stayhub.adapter.out.persistence: SupplierStayEntity, SupplierRoomTypeEntity, SupplierStayJpaRepository, SupplierRoomTypeJpaRepository, StayMappingRepositoryImpl
  - com.stayhub.config: 설정 바인딩 활성화, WebClient 빈, Micrometer 설정
- SK-05 의존 방향. domain 은 아무 패키지도 참조하지 않는다. application 은 domain 만 참조한다. adapter 와 config 는 domain 과 application 을 참조한다. domain 과 application 은 Spring 애노테이션을 쓰지 않는다. 단, application 서비스에 @Service, @Transactional 은 허용한다.

- SK-07 설정 바인딩 클래스

- SK-08 실행 방법은 README 에 적는다. 두 모듈을 각각 bootRun 으로 띄운다. mock-supplier 를 먼저 띄운다.

## 3.2 도메인 모델 (DM)

- DM-01 SupplierCode: enum { A, B }. 소문자 문자열과 상호 변환하는 정적 메서드 fromString 을 둔다. 대소문자를 무시한다. 없는 값이면 IllegalArgumentException.
- DM-02 FailureReason: enum. 각 값은 retryable boolean 을 갖는다.
  - TIMEOUT (retryable)
  - UNAVAILABLE (retryable)
  - RATE_LIMITED (retryable)
  - SUPPLIER_ERROR (retryable)
  - BAD_REQUEST
  - UNAUTHORIZED
  - MALFORMED
  - NO_MAPPING
- DM-03 SupplierResult<T>: 성공 또는 실패를 담는 sealed interface. record Success<T>(T value), record Failure<T>(FailureReason reason, String message). 편의 메서드 isSuccess, isFailure, 정적 팩토리 success(value), failure(reason, message).
- DM-04 StaySearchCriteria: record (LocalDate checkIn, LocalDate checkOut, int adults, int children).
  - nights(): checkIn 부터 checkOut 전날까지의 일수. ChronoUnit.DAYS.between(checkIn, checkOut).
  - stayDates(): checkIn 부터 checkOut 전날까지의 LocalDate 목록. 3박이면 3개.
  - guests(): adults + children.
  - 생성자에서 검증하지 않는다. 검증은 API 계층이 한다.
- DM-05 CatalogEntry: record (String supplierHotelCode, String name, List<CatalogRoomType> roomTypes). CatalogRoomType: record (String supplierRoomTypeCode, String name, int maxOccupancy).
- DM-06 Offer: record (SupplierCode supplier, String supplierHotelCode, String supplierRoomTypeCode, int availableRooms, Price price).
  - 어댑터가 반환하는 표준 형태다. 내부 식별자는 없다. 검색 서비스가 붙인다.
- DM-07 Price: record (long totalAmount, String currency, boolean breakfastIncluded, int nights, List<DailyRate> daily).
  - daily 는 nullable. A 는 채우고 B 는 null.
  - totalAmount 는 세금 포함 총액. 통화 최소 단위 정수.
- DM-08 DailyRate: record (LocalDate date, long nightlyRate, long taxAmount).
- DM-09 Stay: record (long id, SupplierCode supplier, String supplierHotelCode, String name, boolean active). RoomType: record (long id, long stayId, String supplierRoomTypeCode, String name, int maxOccupancy, boolean active).
- DM-10 예약 가능 객실 수 계산은 도메인 정적 메서드로 둔다. Offer 또는 별도 클래스 AvailabilityRule 에 둔다.
  - 입력: 요청 숙박일 목록, 날짜별 잔여 객실 수 Map<LocalDate, Integer>.
  - 규칙: 숙박일 각각에 대해 Map 에서 값을 찾는다. 하나라도 없으면 0. 모두 있으면 최솟값. 음수가 오면 0 으로 본다.
  - 이 메서드를 A 와 B 변환기가 공통으로 쓴다.
- DM-11 포트 인터페이스
  - SupplierCatalogPort: Mono<SupplierResult<List<CatalogEntry>>> fetchCatalog()
  - SupplierAvailabilityPort: Mono<SupplierResult<List<Offer>>> fetchAvailability(List<String> supplierHotelCodes, StaySearchCriteria criteria)
  - SupplierAdapter extends SupplierCatalogPort, SupplierAvailabilityPort: SupplierCode supplierCode()
  - 포트 메서드는 예외를 던지지 않는다. 모든 실패는 SupplierResult.Failure 로 온다. Mono 는 onError 로 끝나지 않는다.
  - fetchAvailability 의 supplierHotelCodes 는 1개 이상 50개 이하다. 호출자가 보장한다. 어댑터는 검증하지 않는다.
- DM-12 StayMappingRepository 포트
  - List<Stay> findActiveStays(SupplierCode supplier)
  - List<Stay> findAllActiveStays()
  - Optional<Stay> findStay(SupplierCode supplier, String supplierHotelCode)
  - List<RoomType> findActiveRoomTypes(long stayId)
  - Optional<RoomType> findRoomType(long stayId, String supplierRoomTypeCode)
  - Stay upsertStay(SupplierCode supplier, String supplierHotelCode, String name): 있으면 name 갱신하고 active=true 로 되돌린 뒤 반환. 없으면 생성.
  - RoomType upsertRoomType(long stayId, String supplierRoomTypeCode, String name, int maxOccupancy): 위와 같다.
  - int deactivateStaysNotIn(SupplierCode supplier, Set<String> supplierHotelCodes): 해당 공급사의 active 숙소 중 집합에 없는 것을 active=false 로 바꾸고 바뀐 수를 반환. 그 숙소의 객실 타입도 모두 active=false.
  - int deactivateRoomTypesNotIn(long stayId, Set<String> supplierRoomTypeCodes): 위와 같다, 객실 타입 단위.
  - Map<Long, Stay> findStaysByIds(Collection<Long> ids), Map<Long, List<RoomType>> findActiveRoomTypesByStayIds(Collection<Long> stayIds): 검색 서비스가 이름을 붙일 때 쓴다.

## 3.3 매핑 저장 (MP)

- MP-01 테이블 supplier_stay
  - id BIGINT 자동 증가 PK
  - supplier_code VARCHAR(16) NOT NULL
  - supplier_hotel_code VARCHAR(64) NOT NULL
  - name VARCHAR(255) NOT NULL
  - active BOOLEAN NOT NULL
  - created_at TIMESTAMP NOT NULL
  - updated_at TIMESTAMP NOT NULL
  - UNIQUE (supplier_code, supplier_hotel_code)
- MP-02 테이블 supplier_room_type
  - id BIGINT 자동 증가 PK
  - stay_id BIGINT NOT NULL, supplier_stay.id 참조 FK
  - supplier_room_type_code VARCHAR(64) NOT NULL
  - name VARCHAR(255) NOT NULL
  - max_occupancy INT NOT NULL
  - active BOOLEAN NOT NULL
  - created_at TIMESTAMP NOT NULL
  - updated_at TIMESTAMP NOT NULL
  - UNIQUE (stay_id, supplier_room_type_code)
- MP-03 JPA 엔티티에 @Table(uniqueConstraints) 로 위 유일 제약을 선언한다. ddl-auto=create 로 기동 때마다 만든다. 인메모리 DB 이므로 마이그레이션 도구는 쓰지 않는다.
- MP-04 created_at, updated_at 은 엔티티가 @PrePersist, @PreUpdate 로 채운다. 시각은 UTC.
- MP-05 StayMappingRepositoryImpl 이 DM-12 포트를 구현한다. 엔티티는 persistence 패키지 밖으로 나가지 않는다. 도메인 record 로 변환해서 반환한다.
- MP-06 식별자는 절대 재사용하지 않는다. 삭제 쿼리는 없다. 비활성화만 있다.

## 3.4 공급사 어댑터 공통 (AD)

- AD-01 WebClientFactory: 공급사 코드를 받아 WebClient 를 만든다.
  - base URL 은 SupplierProperties 에서.
  - 기본 헤더 X-Api-Key 에 apiKey 를 넣는다. 모든 요청에 붙는다.
  - reactor-netty HttpClient 에 연결 타임아웃(integration.connect-timeout)을 건다. 응답 타임아웃은 여기서 걸지 않는다. AD-02 가 건다.
  - 공급사마다 WebClient 하나. 빈으로 두 개 등록하거나 팩토리가 캐시한다.
- AD-02 SupplierCallExecutor: 모든 공급사 호출이 통과하는 한 곳이다. 시그니처는 아래와 같다.

```java
<T> Mono<SupplierResult<T>> execute(
    SupplierCode supplier,
    String api,                     // "catalog" 또는 "availability"
    Duration responseTimeout,
    Mono<SupplierResult<T>> call    // 어댑터가 만든 원 호출. HTTP 오류와 본문 판정까지 끝난 상태
)
```

  - 순서대로 적용한다.
    - call 에 timeout(responseTimeout) 을 건다. TimeoutException 은 Failure(TIMEOUT, "response timeout after {ms}ms") 로 바꾼다.
    - 그 외 예외를 Failure 로 바꾼다. 규칙은 AD-03.
    - 재시도를 건다. 규칙은 AD-04.
    - 지표와 로그를 남긴다. 규칙은 3.11.
  - 반환 Mono 는 절대 onError 로 끝나지 않는다.
- AD-03 예외를 FailureReason 으로 바꾸는 규칙
  - java.util.concurrent.TimeoutException, io.netty.handler.timeout.ReadTimeoutException, io.netty.channel.ConnectTimeoutException: TIMEOUT
  - java.net.ConnectException, java.net.UnknownHostException, io.netty.channel.AbstractChannel.AnnotatedConnectException: UNAVAILABLE
  - org.springframework.web.reactive.function.client.WebClientResponseException: 상태 코드로 판정. 400 BAD_REQUEST, 401 UNAUTHORIZED, 429 RATE_LIMITED, 503 UNAVAILABLE, 500 과 그 외 5xx SUPPLIER_ERROR, 그 외 4xx BAD_REQUEST
  - org.springframework.core.codec.DecodingException, com.fasterxml.jackson 계열 파싱 예외: MALFORMED
  - 그 외: SUPPLIER_ERROR
  - message 에는 예외 클래스 단순 이름과 예외 메시지를 넣는다. 응답 본문이 있으면 앞 200자를 덧붙인다.
- AD-04 재시도
  - Resilience4j Retry 를 쓴다. resilience4j-reactor 의 RetryOperator 로 Mono 에 건다.
  - maxAttempts = integration.retry.max-attempts (기본 2, 즉 원 호출 1회 + 재시도 1회). waitDuration = integration.retry.wait (기본 300ms).
  - retryOnResult: 결과가 Failure 이고 reason.retryable 이 true 일 때만.
  - 예외로는 재시도하지 않는다. AD-02 가 예외를 이미 Failure 로 바꿨으므로 retryOnException 은 쓰지 않는다.
  - 재시도 후에도 실패면 마지막 실패를 그대로 반환한다.
  - Retry 인스턴스는 공급사별로 하나. 이름은 "supplier-a", "supplier-b".
- AD-05 항목 단위 정규화 실패
  - 응답 본문은 파싱됐지만 항목 하나에 필수 필드가 없거나 타입이 틀리면, 그 항목만 버린다. 로그 레벨 WARN 으로 supplier, api, 항목의 식별 가능한 코드, 사유를 남긴다. 나머지 항목은 정상 반환한다.
  - 본문 전체가 파싱되지 않으면 Failure(MALFORMED).
  - 항목 필수 필드는 SA, SB 절에 정의한다.
- AD-06 SupplierRegistry (application 패키지)
  - 생성자로 List<SupplierAdapter> 를 받는다. supplierCode() 로 Map 을 만든다.
  - 같은 코드가 둘이면 생성 시 IllegalStateException.
  - 메서드: Optional<SupplierAdapter> find(SupplierCode), List<SupplierAdapter> all() (SupplierCode 순서로 정렬).

## 3.5 Supplier A 어댑터 (SA)

- SA-01 SupplierAAdapter 는 SupplierAdapter 를 구현한다. supplierCode() 는 A.
- SA-02 목록 조회
  - GET {baseUrl}/a/v1/hotels
  - 응답 DTO: items[] 의 각 항목에 hotelCode, hotelName, roomTypes[] (roomTypeCode, roomTypeName, maxOccupancy)
  - CatalogEntry 변환: hotelCode → supplierHotelCode, hotelName → name, roomTypes 각각 → CatalogRoomType
  - 항목 필수 필드: hotelCode, hotelName. roomTypes 가 없으면 빈 목록으로 본다. 객실 타입 필수 필드: roomTypeCode, roomTypeName, maxOccupancy.
  - SupplierCallExecutor 에 api="catalog", responseTimeout=integration.catalog-response-timeout 으로 넘긴다.
- SA-03 재고·요금 조회
  - GET {baseUrl}/a/v1/availability?hotelCodes={쉼표로 이은 코드}&checkIn={yyyy-MM-dd}&checkOut={yyyy-MM-dd}&adults={n}&children={n}
  - 응답 DTO: items[] 의 각 항목에 hotelCode, hotelName, roomTypeCode, roomTypeName, maxOccupancy, breakfastIncluded, currency, dailyRates[] (date, remainingRooms, nightlyRate, taxAmount)
  - 항목 필수 필드: hotelCode, roomTypeCode, currency, dailyRates. breakfastIncluded 가 없으면 false.
  - SupplierCallExecutor 에 api="availability", responseTimeout=integration.availability-response-timeout.
- SA-04 Offer 변환 (SupplierAMapper)
  - availableRooms: DM-10 규칙. 입력 Map 은 dailyRates 의 date → remainingRooms.
  - price.totalAmount: 요청 숙박일에 해당하는 dailyRates 각각의 nightlyRate + taxAmount 를 합산. 요청 숙박일이 dailyRates 에 없으면 그 항목의 availableRooms 는 이미 0 이므로 totalAmount 는 있는 날짜만 합산해 둔다. 어차피 검색 결과에서 제외된다.
  - price.currency: currency 그대로. price.breakfastIncluded: breakfastIncluded. price.nights: criteria.nights().
  - price.daily: 요청 숙박일 순서대로 DailyRate(date, nightlyRate, taxAmount). 없는 날짜는 건너뛴다.
  - 검증 예시: dailyRates 가 (120000+12000), (150000+15000), (120000+12000) 이면 totalAmount 429000. remainingRooms 3, 1, 5 면 availableRooms 1.
- SA-05 실패 판정 (SupplierAFailureMapper)
  - HTTP 상태 코드로 판정한다. AD-03 의 WebClientResponseException 규칙과 같다. WebClient 의 onStatus 를 쓰지 않고 예외를 흘려보내 AD-02 가 처리하게 해도 된다. 어느 쪽이든 결과는 같아야 한다.
  - 본문의 error 필드가 있으면 message 에 "{status} {error}: {message}" 형태로 넣는다.

## 3.6 Supplier B 어댑터 (SB)

- SB-01 SupplierBAdapter 는 SupplierAdapter 를 구현한다. supplierCode() 는 B.
- SB-02 목록 조회
  - GET {baseUrl}/b/api/properties
  - 응답 DTO: resultCode, resultMessage, data { items[] (propertyId, propertyName, rooms[] (roomId, roomName, maxOccupancy)) }
  - CatalogEntry 변환: propertyId → supplierHotelCode, propertyName → name, rooms 각각 → CatalogRoomType(roomId, roomName, maxOccupancy)
  - 항목 필수 필드: propertyId, propertyName. 객실 타입 필수 필드: roomId, roomName, maxOccupancy.
  - api="catalog", responseTimeout=integration.catalog-response-timeout.
- SB-03 재고·요금 조회
  - GET {baseUrl}/b/api/search?propertyIds={쉼표로 이은 코드}&checkIn={yyyy-MM-dd}&checkOut={yyyy-MM-dd}&adults={n}&children={n}
  - 응답 DTO: resultCode, resultMessage, data { items[] (propertyId, propertyName, roomId, roomName, maxOccupancy, breakfastIncluded, currency, totalPrice, taxIncluded, inventory[] (date, remainingRooms)) }
  - 항목 필수 필드: propertyId, roomId, currency, totalPrice, inventory. breakfastIncluded 가 없으면 false. taxIncluded 는 읽지 않는다.
  - api="availability", responseTimeout=integration.availability-response-timeout.
- SB-04 Offer 변환 (SupplierBMapper)
  - availableRooms: DM-10 규칙. 입력 Map 은 inventory 의 date → remainingRooms.
  - price.totalAmount: totalPrice 그대로. price.currency: currency. price.breakfastIncluded: breakfastIncluded. price.nights: criteria.nights(). price.daily: null.
  - 검증 예시: totalPrice 452000 이면 totalAmount 452000. inventory 3, 1, 5 면 availableRooms 1.
- SB-05 실패 판정 (SupplierBFailureMapper)
  - HTTP 상태가 200 이 아니면 AD-03 의 상태 코드 규칙을 그대로 쓴다. 스펙상 항상 200 이지만 방어적으로 둔다.
  - HTTP 200 이면 본문 resultCode 로 판정한다.
    - "0000": 성공. data.items 를 쓴다. data 가 null 이면 MALFORMED.
    - "E400": BAD_REQUEST
    - "E401": UNAUTHORIZED
    - "E429": RATE_LIMITED
    - "E500": SUPPLIER_ERROR
    - "E503": UNAVAILABLE
    - 그 외 값: SUPPLIER_ERROR
    - resultCode 필드가 없음: MALFORMED
  - message 에는 "{resultCode} {resultMessage}" 를 넣는다.

## 3.7 카탈로그 동기화 (SY)

- SY-01 SyncSupplierCatalogService.sync(SupplierCode) → SyncResult
  - SyncResult: record (SupplierCode supplier, int added, int updated, int deactivated, FailureReason failureReason, String failureMessage). 성공이면 failureReason 은 null.
- SY-02 처리 순서
  - SupplierRegistry 에서 어댑터를 찾는다. 없으면 IllegalArgumentException.
  - fetchCatalog() 를 block(integration.catalog-response-timeout + 1s) 으로 기다린다. Mono 는 Failure 로 오지 예외로 오지 않으므로 block 자체는 타임아웃 예외를 낼 수 있다. 그 경우 Failure(TIMEOUT) 으로 취급한다.
  - Failure 면 DB 를 건드리지 않고 SyncResult 에 failureReason 을 채워 반환한다. 기존 매핑은 그대로다.
  - Success 면 하나의 트랜잭션 안에서 아래를 수행한다.
    - 각 CatalogEntry 에 대해 upsertStay. 이전에 없던 것이면 added 증가, 있던 것이면 updated 증가.
    - 각 CatalogRoomType 에 대해 upsertRoomType.
    - 그 숙소의 객실 타입 중 목록에 없는 것을 deactivateRoomTypesNotIn.
    - 마지막에 deactivateStaysNotIn 으로 목록에 없는 숙소를 비활성화. 반환값을 deactivated 에 더한다.
  - 트랜잭션 안에서 예외가 나면 롤백되고 예외가 밖으로 나간다. 호출자가 처리한다.
- SY-03 목록이 비어 있어도(items 가 빈 배열) 성공으로 본다. 그 공급사의 모든 숙소가 비활성화된다. 이건 의도된 동작이다.
- SY-04 기동 시 동기화 (StartupCatalogSync)
  - ApplicationRunner 로 구현한다. integration.sync-on-startup 이 true 일 때만 동작한다.
  - SupplierRegistry.all() 순서로 순차 실행한다. 병렬로 하지 않는다. 단순함이 우선이다.
  - 각 결과를 INFO 로 로그한다. 실패해도 예외를 던지지 않는다. 앱은 정상 기동한다.
  - 트랜잭션 예외(SY-02 마지막 항목)도 잡아서 ERROR 로 로그하고 다음 공급사로 넘어간다.
- SY-05 수동 동기화 API
  - POST /internal/suppliers/{supplierCode}/sync. supplierCode 는 대소문자 무시. 본문 없음.
  - 200: SyncResult 가 성공일 때. 응답 본문 { "supplier": "A", "added": 2, "updated": 0, "deactivated": 0 }
  - 404: 알 수 없는 공급사. 본문 { "code": "UNKNOWN_SUPPLIER", "message": "unknown supplier: X" }
  - 502: 공급사 호출이 실패했을 때. 본문 { "code": "SUPPLIER_UNAVAILABLE", "message": "..." }. code 는 "SUPPLIER_" + FailureReason 이름.
  - 500: 트랜잭션 예외. 본문 { "code": "INTERNAL_ERROR", "message": "..." }
- SY-06 목록 API 호출에도 AD-04 재시도가 적용된다. 별도 처리는 없다.

## 3.8 검색 서비스 (SR)

- SR-01 SearchStaysService.search(StaySearchCriteria) → SearchResult
  - SearchResult: record (StaySearchCriteria criteria, List<SearchItem> items, List<SearchFailure> failures)
  - SearchItem: record (long stayId, String stayName, long roomTypeId, String roomTypeName, int maxOccupancy, int availableRooms, SupplierCode supplier, Price price)
  - SearchFailure: record (SupplierCode supplier, FailureReason reason, String message)
- SR-02 처리 순서. 이 순서를 지킨다.
  - 검색 ID 를 UUID 로 만들어 MDC 키 searchId 에 넣는다. 끝나면 지운다.
  - findAllActiveStays() 로 active 숙소를 가져와 공급사별로 묶는다.
  - SupplierRegistry.all() 의 각 공급사에 대해
    - 그 공급사의 active 숙소가 0개면 SearchFailure(supplier, NO_MAPPING, "no active stays for supplier") 를 추가하고 호출하지 않는다.
    - 숙소 코드를 integration.chunk-size 개씩 청크로 나눈다. 순서는 stayId 오름차순. 청크에 0 부터 번호를 붙인다.
    - 청크마다 어댑터의 fetchAvailability(코드들, criteria) 를 만든다. 결과를 ChunkResult(supplier, chunkIndex, SupplierResult<List<Offer>>) 로 감싼다.
    - Flux.fromIterable(청크들).flatMap(청크 → Mono<ChunkResult>, integration.chunk-concurrency) 로 공급사 안 동시성을 제한한다.
  - 공급사별 Flux 를 Flux.merge 로 합친다. 공급사 간에는 제한이 없다.
  - .take(integration.search-budget) 을 걸고 collectList().block() 한다. 예산이 지나면 그때까지 도착한 ChunkResult 만 남고 나머지는 취소된다.
  - 도착하지 않은 청크마다 실패로 본다. 사유는 TIMEOUT, message 는 "search budget exceeded".
  - 실패한 청크(Failure 결과 또는 도착 안 함)를 공급사별로 모아 SearchFailure 하나로 만든다. reason 은 그 공급사의 첫 실패 청크의 reason. message 는 "{실패 청크 수}/{전체 청크 수} chunks failed: {첫 실패 message}".
  - 성공한 청크의 Offer 들을 모은다.
  - 각 Offer 에 대해 findStay(supplier, supplierHotelCode) 와 findRoomType(stayId, supplierRoomTypeCode) 로 내부 식별자를 찾는다. 성능을 위해 미리 findStaysByIds, findActiveRoomTypesByStayIds 로 Map 을 만들어 두고 메모리에서 찾아도 된다. 둘 중 하나라도 없거나 active 가 아니면 그 Offer 를 버리고 WARN 로그를 남긴다.
  - stayName, roomTypeName, maxOccupancy 는 매핑 DB 의 값을 쓴다. 공급사 재고 응답의 이름은 쓰지 않는다. 단일 출처 원칙이다.
  - criteria.guests() 가 maxOccupancy 보다 크면 그 Offer 를 버린다. 공급사가 걸러 준다고 믿지 않고 한 번 더 거른다. 로그는 남기지 않는다.
  - availableRooms 가 0 이면 버린다.
  - 남은 것을 SearchItem 으로 만든다. 정렬은 supplier 이름 순, 그 다음 stayId 오름차순, 그 다음 roomTypeId 오름차순. 결정적 순서가 테스트에 필요하다.
  - SearchResult 를 반환한다.
- SR-03 block 은 이 메서드 안에서 정확히 한 번만 호출된다. 다른 곳에서는 block 을 쓰지 않는다. 단, SY-02 의 동기화는 별도 흐름이므로 예외다.
- SR-04 청크 나누기는 정적 유틸 메서드로 분리한다. 입력 120개면 50, 50, 20 세 청크. 입력 50개면 청크 하나. 입력 0개는 호출되지 않는다.
- SR-05 한 공급사의 청크 일부만 실패해도 나머지 청크의 Offer 는 정상 반환한다. failures 에는 그 공급사가 한 번 들어간다.

## 3.14 구현 규칙

- 요구사항 원문 파일을 커밋하지 않는다. .gitignore 에 *.pdf 를 둔다.
- 커밋 메시지 형식: {type}: {ID} {요약}. 예: feat: SA-04 A 응답을 Offer 로 변환. type 은 feat, test, refactor, docs, chore.
- 커밋 메시지에 Co-Authored-By 트레일러를 넣지 않는다.
- 스펙에 없는 기능을 추가하지 않는다. 필요하다고 판단되면 JOURNAL 에 적고 사용자에게 묻는다.
- 스펙과 충돌하는 구현이 더 낫다고 판단되면 구현하지 말고 JOURNAL 에 적고 사용자에게 묻는다.
- 테스트를 지우거나 @Disabled 로 막아서 통과시키지 않는다.
- 외부 라이브러리는 SK-02 목록 밖에서 추가하지 않는다. 필요하면 묻는다.
- block() 은 SR-03 과 SY-02 두 곳에서만 쓴다.
- 모르는 코드가 저장소에 남지 않도록, 각 단계가 끝나면 무엇을 만들었고 왜 그렇게 했는지 JOURNAL 에 한 줄 이상 적는다.
